## Active memory

- Why (2026-11-04): Halo projects are James's main bottleneck. Project information arrives from several places: each project's Slack channel, Halo actions and emails, Outlook, 3CX calls, and scheduling.
- Chosen design: option C, live watching. Each Halo project becomes one long-running superagent ticket. New activity in the project's Slack channel and in Halo goes to that project's worker. The worker raises only what needs James in `#ai-james`. Options A (on demand) and B (daily digest) were not chosen.
- Team boundary: superagent must not bother the team. It never posts in project channels and replies only in `#ai-james`. It must still read every teammate's message there (James, 2026-11-04): project channels are a common place work gets assigned to him, so a teammate's post can start or update his work. It works only on James's projects: the assigned technician shows in Halo and in each project's Slack channel. All projects are currently James's, but a project may be assigned to a teammate.
- Project channels follow names such as `#rce---network-modernization-2026` and `#cpti-bss-transition-2026` (mostly public). James approved Nathan joining them (Slack shows one "joined" message).
- Autonomy: everything is a draft to start (client emails, Halo updates, appointments). James's existing instructions in `~/Documents/itastack` (`AGENTS.md`, `memory/rules.md`, including the email and Halo client-reply drafting row) define how drafts are made; superagent should follow those, not new rules.
- How James talks to it (2026-11-04): Slack only for now, not a DSH session, a herdr/pi tab or a Slack DM. Every Slack message goes through the router.
- Questions (2026-11-04, option A): the router can't answer by itself, so a question becomes a small ticket that a worker answers through itastack. Added as text in the team "Ticket scope" prompt (prompt revision 2), with no code change. Routing a message to a project's existing ticket by name (option B) waits for option C. A ticket ends when its worker reports ready (completed); a later reply in its thread reopens it. `stop` in the thread ends it early.
- Visible-work exception (James, 2026-11-04): itastack's rule that research and changes happen only in a visible pi/herdr tab does not block superagent; its workers count as visible because James steers them in Slack. Written into the team "Ticket scope" prompt (revision 3), not into itastack's shared files. Changes still need James's yes in the thread.
- Purpose (James, 2026-11-04): superagent is one candidate to replace startday's poll loop, and possibly startday as a whole; `dispatch.py` will be removed from startday. startday's pi poll loop was removed on 2026-11-04 (`poll.py`, `runner.json` and their tests deleted; backup `~/.local/share/itastack-backups/startday-poll-removal-2026-11-04.tgz`); Start runs `dispatch.py` once, by hand after that. Treat `~/Documents/itastack/.agents/skills/startday` as the reference for what to replace: its Halo rules (book, reply_owed, close_out, overdue_task, end-user note, 7-day idle, left queue), the scheduled-and-acknowledged skip, one tab per ticket, and the 3-tab cap. Superagent has Slack, Feishu and GitHub sources but no Halo source. The Halo side watches all of James's tickets, matching startday, not projects only (James, 2026-11-04). Build approach (James, 2026-11-04): one 15-minute watcher that reads only and never posts outside `#ai-james`; James invites Nathan by hand to the project channels it should watch. Watched sources, each applying to tickets and projects: Halo, those project channels (teammates included), James's Outlook inbox outside junk (most project email never reaches Halo), his 3CX calls, and new meetings in `~/Documents/itastack/Meetings` (processed with the itastack `meeting` skill). Workers may read and write research files the way a Research Tab does (James, 2026-11-04): the research file stays the shared record so he can still pick any item up in pi; Slack is the conversation. Approvals: he says yes in the Slack thread and the worker records it through `sd.py`. Email: Inbox only (his replies sit in its threads), not Junk or Sent. 3CX: every call is transcribed; `calls.list` (tenant `ita`) returns `Transcription` and `Summary`, and the itastack `3cx-summary` skill turns one into a Halo note. Meetings: a recording takes about a minute to copy from Windows into `Meetings/`, so the watcher waits for it to settle (the `meeting` skill's `list` marks `settling`).
- Reachable through itastack MCP (checked 2026-11-04, read-only): Halo (tickets, actions, appointments including `find_free_slot`, ticket email), M365 (tenant `ita`, among others), 3CX (tenant `ita`), Exchange (tenant `omep` only). Whether M365 reads James's own mailbox, and what 3CX exposes for call logs, is not yet verified. The Slack bot's scopes include channel history, join and DMs (`im:history`).

- Fork internals that shape any watcher build (verified 2026-11-04 in a 4-model plan review): the router accepts only candidates whose assessment says an implementation was requested with a settled target (`src/policy.ts` `directionAllowed`), so watcher news is ignored unless a rule or the admission prompt says it counts; `bindThread` adds a followed thread that keeps a ticket from ending until the thread closes, so it is not a reply-routing tool; workers have no Slack posting tool (only `orchestrator_report`, relayed by the router session); `commands.run` kills a subprocess after 90 s; a Slack thread is one top-level message, so each channel post is its own thread unless mapped; an ended ticket stays subscribed and a person's reply in its thread resumes it.

- Project channel to Halo project mapping (James, 2026-11-04): set by hand per channel when Nathan is invited, as a `Halo project #` field on the Slack channel row in superagent settings; a channel set to listen to all posts must name one. After the plan review James chose to revise the watcher plan rather than drop superagent.

- Watcher installed 2026-11-04 (fork `ita-slack` at `21c13a0`): user timer `ita-watch.timer` (units symlinked from `~/src/dsh-superagent/scripts/ita-watch/`, weekdays 07:00-16:45 every 15 min) writes `~/.dsh/state/superagent/ita-{watch.json,spool.jsonl,watch-status.json}`. The `ita` Source is enabled in the profile patch (`dsh-superagent-ita`) with home `C09L1QNKKDF`, acting for `UC7150R96`, `statusFile` set, and `dryRun: true` (watching only: nothing is posted). Pause: `systemctl --user stop ita-watch.timer`, or the `ita` Source off. Going live is plan Task 4 (worker prompts) then `dryRun: false`.
- Project channels mapped 2026-11-04 (Slack Source settings, revision 2), each `listen: all` with the Halo **parent project** number, which matches the watcher's `halo:<parent>` item for project tasks: osig-3cx_migration 66390, rce---network-modernization-2026 66867, cbw-decommission-hv1 69363, tcfn-ipads-and-mdm 69274 (no parent; the ticket itself), lcc-pdx-office-move 69543, hlwd-email-security 70919, hlwd-mm-battery-backup 70920, tcfn-iphones-and-mdm 70984. Each channel's purpose holds `Ticket URL` (the project's task ticket) and `Tech:`. Not mapped (no ticket in the purpose): hlwd-mm_relocation, sevco-triage, prospect-basis_point, nathan; the other `ai-*` channels are Hermes-era and stay unlisted. James decided (2026-11-04) to keep all eight linked, including Kevin's (rce, cbw, lcc): he is the only one who mainly uses `@Nathan`.
- Quiet threads (James, 2026-11-04; fork `ita-slack` at `0e312c1`): news reaches a worker without any post. An item's `#ai-james` thread opens only when its ticket first has something for James (no starter post, "Watcher:" line or acknowledgement), and a dry run holds posts until going live. James's own project-channel posts are background for the next teammate post, not news. Calls, voicemails and mail are matched to a Halo client by caller number or sender address and land on one item per client, `client:<id>`, whose worker works out which ticket each is about. Shared mail domains (gmail etc.) and searches matching more than one client stay unmatched. Noise such as sales mail is dropped by the worker (plan Task 4), not by filters. The one call filter is talk time: over 10 s reaches a worker (James: any call of substance is longer). James chose this after an eval of the first 13 held items: about 20 posts for 2 that needed him, and Elaine's two calls landed in separate threads.
- Halo `users.list` search matches a bare 10-digit phone number (`5033803445` finds Elaine, client 51) and `@domain`. A search that finds no one (or a dashed number) answers with an empty body, which `halo.py` raises as "MCP returned no JSON payload"; the watcher treats it as no match (fork `d2a1d30`, after it failed the 07:45 and 08:00 rounds on 2026-11-05). Halo's own ticket mail writes the number zero-padded in the subject, `[ID:0070966]`.
- Watcher and startday (James, 2026-11-05, option A): `watch.py` keeps its own copy of startday's Halo rules (`classify`, `REASONS`, `LEFT_QUEUE`, status constants; fork `d29b27e`) and imports only startday's `halo.py` and `sd.py`. Nothing asks Jev: workers drop the noise. Why: itastack removed `dispatch.py` on 2026-11-05 and every round crashed from 13:45. A grep inside itastack can't see the watcher, so the itastack session owning that cleanup (w12:pC) was sent the list of `halo.py`/`sd.py` names it uses. Rounds run only 07:00-17:00 Mon-Fri; to test outside those hours, run `watch.py round` on copies of the state and spool in `/tmp` with `--now` set inside them.
- Gotcha: `check_recent_mail` returns the newest 100 Inbox messages, so when mail leaves the Inbox, months-old mail moves into view. The watcher skips mail received more than 1 h before its last good round.
- Gotcha: the ITAStack 3CX `calls.list` tool answers a window with no calls with an empty body (`text: ""`, no structured content), not `[]`; startday's `halo.py` turns that into "MCP returned no JSON payload". The watcher treats it as no calls (fork commit `1d38f3b`).
