# Shard a Plan

> **Canonical paths (MANDATORY):** Read `~/.pi/agent/skills/PATHS.md` before any file output. All artifact paths in this skill resolve through that reference. Deviation is a bug — surface it instead of working around it.

Use this skill when a plan exceeds a single-session execution budget — typically when it contains 20+ tasks, spans many files, or its raw size suggests context exhaustion during build. Output is a set of `shard-N.md` files plus a `README.md` index, co-located with the original plan in `artifacts/plans/{slug}/`.

Do not use this skill for small plans. The default behavior is **estimate, then advise** — only produce shards when the budget is actually exceeded. A no-op report ("plan fits in one session") is a valid outcome.

---

## Variables

- `PATH_TO_PLAN` — explicit plan path (optional; if omitted, discover the most recent plan)
- `PLAN_DIRECTORIES` — `artifacts/plans/`
- `SLUG` — derived from the plan's parent directory (e.g., for `artifacts/plans/add-auth/plan.md`, slug is `add-auth`)
- `BUDGET_TOKENS` — `120000` (token budget per shard; conservative default that leaves room for tool output)
- `FORCE_FLAG` — accept `--force` arg to shard a plan that fits the budget (rare; useful for testing the shard pipeline)

---

## Workflow Overview

1. Discover and read the plan
2. Estimate token consumption
3. Decide: fits in one session, or shard?
4. If shard: propose splits at dependency seams
5. Confirm splits with user
6. Generate shard files + README + preserved original
7. Report

---

## Phase 1 — Discover the Plan

If `PATH_TO_PLAN` is provided, use it.

If not, use `bash` to find recent plans:

```sh
find artifacts/plans -name 'plan.md' 2>/dev/null | xargs ls -t 2>/dev/null | head -10
```

Present 1–3 candidates with `ask_user` (type: select). If none found, ask the user for a path.

Once selected, derive `SLUG` from the parent directory. Use `read` to inspect the plan.

---

## Phase 2 — Estimate Token Consumption

Use this heuristic on the plan markdown:

| Component | Tokens (rough) |
|-----------|----------------|
| Plan body (per 1000 chars) | 250 |
| Per task in `## Step by Step Tasks` | 1500 (reasoning + reads + small edits) |
| Per task that touches a new file | +1500 |
| Per task that touches an existing large file | +3000 |
| Per validation command in `## Validation Commands` | 500 |
| Per test scaffold called out in `## Tests` | 1000 |
| Fixed overhead (orchestrator + status updates) | 5000 |

Sum the components. This is a one-shot execution estimate, not an exact count.

Report the estimate before deciding:

```text
Token estimate: ~<N> (budget: 120000)
Tasks: <count>, files touched: <count>, validation commands: <count>
```

---

## Phase 3 — Decide

If `estimate <= BUDGET_TOKENS` and `--force` was not passed:

- **Report no-op (Format A) and stop.** The plan fits — `pi-dev-build` can execute it in one session.

If `estimate > BUDGET_TOKENS` or `--force` was passed:

- Continue to Phase 4 to propose shards.

---

## Phase 4 — Propose Shard Splits

Read the plan's `## Step by Step Tasks` to identify natural seams:

1. **Phase boundaries.** If the plan uses `### N. Phase Name` subsections, prefer splitting on those.
2. **Dependency boundaries.** Tasks marked `[sequential]` or with explicit `**Dependencies:**` lines define hard ordering.
3. **File-cluster boundaries.** Tasks that all touch the same module/subdirectory often belong in one shard.
4. **Token-budget boundaries.** No shard may exceed `BUDGET_TOKENS`. If a single phase exceeds the budget, split it further.

**Rules:**
- A task may not be split across shards. Either it's in shard N or shard N+1.
- Shards are sequential. Shard N+1 may assume shard N is fully complete.
- Each shard must be independently verifiable — its own validation commands run after the shard, not at the end of all shards.
- Final shard concludes with the plan-level `## Acceptance Criteria` validation.

Present proposed splits with `ask_user` (type: select):

```yaml
ask_user:
  type: select
  question: |
    Proposed shard split (estimated <total> tokens, budget <BUDGET_TOKENS> each):

    Shard 1: <name> (~<N> tokens) — tasks [1.1] through [1.4]
    Shard 2: <name> (~<N> tokens) — tasks [2.1] through [2.5]
    Shard 3: <name> (~<N> tokens) — tasks [3.1] through [3.3]

    Accept this split?
  options:
    - "Accept"
    - "Let me adjust"
    - "Cancel"
```

If the user adjusts, use `ask_user` (type: input) to capture revised boundaries, then re-confirm.

---

## Phase 5 — Generate Shard Files

For each shard, write `shard-N.md` to `artifacts/plans/${SLUG}/shard-N.md`.

### Shard file format

```md
---
slug: <slug>
shard: <N>
of: <total>
parent_plan: artifacts/plans/<slug>/original-plan.md
depends_on_shard: <N-1, or "none">
estimated_tokens: <N>
---

# Shard <N> of <total>: <Shard Name>

**Parent plan:** [original-plan.md](original-plan.md)
**Run command:** `pi-dev-build artifacts/plans/<slug>/shard-<N>.md`
**Previous shard:** [shard-<N-1>.md](shard-<N-1>.md) — must be complete before running this
**Next shard:** [shard-<N+1>.md](shard-<N+1>.md)

## Shard Context (assumed already complete)

Tasks completed in earlier shards that this shard depends on:
- [1.1] <description>
- [1.2] <description>

## Tasks for This Shard

### <Phase name from original plan>
- [ ] [N.M] <task verbatim from original plan>
- [ ] [N.M] <task verbatim>

## Relevant Files (this shard)

<subset of original plan's Relevant Files that apply to tasks in this shard>

## Validation Commands (this shard)

<subset of original plan's Validation Commands that apply to tasks in this shard>

## Acceptance Criteria (this shard)

This shard is complete when:
- All tasks above are checked off in this file AND propagated back to the original plan
- This shard's validation commands all pass
- The next shard can proceed

The plan-level Acceptance Criteria is validated by the final shard.
```

### Preserve original

Copy the original plan to `artifacts/plans/${SLUG}/original-plan.md` (do NOT delete `plan.md` — keep both; `plan.md` is the live one, `original-plan.md` is the snapshot at shard time).

Actually: rename `plan.md` → `original-plan.md` and let `pi-dev-build` work off the shards. The shards are the new operational truth; the original is preserved for reference. Update the README to make this explicit.

```sh
mv "artifacts/plans/${SLUG}/plan.md" "artifacts/plans/${SLUG}/original-plan.md"
```

### README index

Write `artifacts/plans/${SLUG}/README.md`:

```md
# <Plan title> — Sharded

The original plan was sharded because its estimated token consumption exceeded
the single-session budget. Run shards in order. Each shard depends on its
predecessor being complete.

## Execution Order

| # | Shard | Tokens | Tasks | Run Command |
|---|-------|--------|-------|-------------|
| 1 | [Shard 1: <name>](shard-1.md) | ~<N> | <count> | `pi-dev-build artifacts/plans/<slug>/shard-1.md` |
| 2 | [Shard 2: <name>](shard-2.md) | ~<N> | <count> | `pi-dev-build artifacts/plans/<slug>/shard-2.md` |
| ... | ... | ... | ... | ... |

## Total Coverage

- Total tasks: <N> (sum across all shards = original plan task count)
- Total tokens (estimated): <N>
- Budget per shard: <BUDGET_TOKENS>

## Original

See [original-plan.md](original-plan.md) for the unsharded plan.
```

---

## Phase 6 — Report

### Format A (no-op, plan fits)

```text
Dev Shard Analysis — No Sharding Needed

Plan: artifacts/plans/<slug>/plan.md
Estimated tokens: <N> (budget <BUDGET_TOKENS>)
Tasks: <N>, files: <N>

Verdict: This plan fits in a single execution session.

Next step:
  pi-dev-build artifacts/plans/<slug>/plan.md
```

### Format B (sharded)

```text
Dev Shard Complete

Original plan: artifacts/plans/<slug>/original-plan.md  (renamed from plan.md)
Estimated tokens: <N> (exceeded budget of <BUDGET_TOKENS>)

Sharded into <N> shards:

  artifacts/plans/<slug>/
  ├── README.md          (index + run order)
  ├── shard-1.md         ~<N> tokens — <summary>
  ├── shard-2.md         ~<N> tokens — <summary>
  ├── shard-N.md         ~<N> tokens — <summary>
  └── original-plan.md   (preserved reference)

Run in sequence:
  1. pi-dev-build artifacts/plans/<slug>/shard-1.md
  2. pi-dev-build artifacts/plans/<slug>/shard-2.md
  ...
  N. pi-dev-build artifacts/plans/<slug>/shard-N.md

Each shard depends on the previous being fully complete (tasks checked, validation passed).
```

---

## Notes

- **No half-shards.** A task is either in shard N entirely or it's not in shard N at all. Splitting a task across shards breaks the build's task-completion model.
- **Shards are linear.** Don't try to parallelize shards — they exist because context is the constraint, and a parallel shard would still need the previous shard's outputs in context.
- **Original is preserved.** `original-plan.md` is the snapshot at shard time. If the user revises the plan after sharding, they need to re-shard or manually reconcile.
- **`plan.md` becomes `original-plan.md`.** After sharding, the directory no longer has a `plan.md` — `pi-dev-build` operates on `shard-N.md` files. This is intentional: a sharded plan should not be runnable as a single plan, because that would defeat the purpose.
- **Budget is conservative.** `120000` leaves room for tool output, status messages, and verification reads on top of the raw plan. If shards consistently come in well under budget at runtime, the budget can be tightened (which would split fewer plans).
