# Tracking model (before filing old notes)

Fit the agent or bot to the owner's purpose. Recommend from what they already said; otherwise ask: **"What people or things do you keep coming back to, and what do you need remembered about each?"** Settle the organization before sorting old notes. In a separate project, apply the adjustments below.

## Choose the organization

- **Independent projects, no clients:** use `projects/<short>/README.md` for each real body of work. Set `client_folder` to `projects` when lasting facts about those projects also need tracked memory.
- **Client work:** keep `clients/<short>/` for client documents. Independent work can still use `projects/<short>/README.md`; do not put it under a pretend client. Keep `client_folder` as `clients` for client memory and use project READMEs as entry points for independent work.
- **Another recurring thing:** use the owner's word, such as `students`, `properties` or `devices`. Choose document folders for that work; projects remain available when useful.
- **Nothing recurring yet:** remove the unused tracked-thing loading row, leave `client_subjects` empty and do not create fictional records. Keep the project convention available for later.

The existing `client_*` schema keys, `type: client-memory`, glossary heading `## Clients` and index heading `## Client Hubs` remain internal compatibility names. Speak to the owner using their word. One schema has one tracked-memory collection; do not promise separate simultaneous client and project hub collections. An independent project in a client workspace uses its README and existing memory/decision links, not a second invented schema. A memory topic named `projects` is independent of `client_folder: projects`: `memory/workflows/projects/` and `memory/projects/` have different jobs.

## Agree the layout and memory

1. **Tracked folder.** Use one lowercase folder name, usually plural, in `client_folder`; it defaults to `clients`. Set it before creating notes. For existing data, propose changes and obtain approval first. Preserve exact previous hand-written memory using personal-memory reference.md "Recovery before editing". Check destination conflicts and preserve both sides before moving either `memory/<old-folder>/` or root `<old-folder>/`; never edit an external source. Use `git mv` when available, otherwise verified file tools. Rebuild hubs and fix affected pointers. If an installed integration hardcodes `clients/`, explain the limitation and offer to leave it unused; do not silently force a non-client workspace back to client folders or claim that integration works.
2. **Document folders.** Choose `client_dirs` for the actual work, not by renaming the client defaults. A project starting point is `["research", "design", "procedures"]`; retain only what the owner needs, including `[]` for README-only projects. Values are unique lowercase folder names (letters, digits, hyphen), never paths. Client work may keep tickets/projects/procedures/meetings/templates. Create folders only when used. Research confined to one project uses its configured research folder; cross-project research uses root `research/`, unless the owner or a skill names another path. Retain an existing folder containing files until its approved migration is complete; never drop it to satisfy a new layout.
3. **Project entry point.** For each real project, use the Project README format in personal-memory's installed `supporting-templates.md`. It records the goal, scope, completion check, related task IDs/paths, files and authoritative memory/procedure links. Read it before project work. Use existing project documentation instead of duplicating it. Propose real initial projects from the owner's work; do not populate example projects.
4. **Lasting subjects.** Propose only the kinds of lasting facts the owner needs, usually 3 to 6 lowercase subjects, such as setup, constraints or conventions. These are not project status or task history. With approval, add them to `client_subjects`; retain existing subjects until their notes have an approved new home. If no lasting facts are needed, leave subjects empty and use the README without a hub.
5. **Procedure and decision topics.** Review `topics` with the purpose in mind; suggest useful additions, such as printing or household, with owner approval. Preserve topics used by existing files. Empty workflow indexes are expected until a procedure is actually verified and approved. Agent procedures live in `memory/workflows/<topic>/<slug>.md`; a project's `procedures/` holds human runbooks or links, never an automatically executable lead. Unverified recipes remain proposals in `notes/`. Skills stay reusable capabilities, not a replacement for owner-specific procedures.
6. **Wire the agreed homes.** Put tracked short names and identities under `## Clients` in the glossary. Add the owner's term to `CONTEXT.md` when it needs a definition. Retarget the tracked-thing row in `memory/rules.md` to the owner's word and `memory/<client_folder>/_hubs/<short>.md`, only when durable tracked notes exist; a hub is generated from notes, not just documents. Update the folder map to describe both independent projects and the selected tracked collection. Keep a single project path when `client_folder` is already `projects`. Preserve `tasks/` as the saved-work home; link its records from READMEs, never maintain duplicate task status in memory. Keep or add a project-work row in `memory/rules.md` loading the folder map, so starting or continuing a project opens its relevant README. The map must say this even when no durable hub exists.
7. **Prove only what exists.** After approval, open one real project's README and verify its file/task links. If there is a grounded lasting fact, save it with personal-memory, run `hubs.py`, add the hub row under `## Client Hubs` in `memory/index.md`, and verify that README and configured document links appear. Run `indexes.py` and `gate.py --memory memory audit`. With no real project or durable fact yet, check the agreed folder map/schema and empty indexes, omit the nonexistent hub pointer, and report that populated project/hub behavior has not been exercised. Setup can finish; never invent a fact, project, approval date or verified procedure as proof.

Without Python, write indexes/hubs by hand following personal-memory, verify existing links and required fields, and disclose that automated checks were not run. Without exact preservation or sufficient file tools, stop the affected edit. Revisit the model when the owner's work changes; upgrades preserve these choices rather than restoring client defaults.

## Applying this outside a full workspace

Use the `<skills>` location selected by memory-setup. A code repository keeps its existing project README, document layout and backlog; propose additions rather than nesting it under a new `projects/`. Do not create a folder map when the project does not need one. Settle the model before sorting, but write no migrated facts or proof note until memory-setup step 6 approval. Existing `memory/` keeps its content; get approval for schema changes and renames separately. If no tracked-thing loading row exists, add one only when notes and a hub exist. Otherwise there is nothing to delete. Git, Python and extra tools remain optional.
