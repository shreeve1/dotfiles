# Memory setup

Give the folder memory that fits its owner. Git, Python and subagents are optional; use the available file tools when they are absent. Never install tools without the owner's OK.

`<skills>` means the folder holding `personal-memory`: `.agents/skills` for a workspace or project copy, `~/.agents/skills` for a global install. In the commands below, `python3` means `python` where that is the working command (often on Windows). Run commands from the target folder; substitute the chosen path and quote paths containing spaces for the owner's shell.

1. **Look at what's there.** Read the target folder's instructions and any `memory/`; identify code and git if present. Read the named source, if any. Ask what the owner wants remembered and where the old material is; ask them to paste or export saved memories or instructions an app keeps out of reach. Check tool availability only when needed.
2. **Settle skills and tracking.** In a starter workspace, use its existing `.agents/skills/`. Otherwise check for `~/.agents/skills/personal-memory/SKILL.md` (under the user profile on Windows), asking the owner if the session cannot check. Before selecting any project or global install, verify readable `SKILL.md`, `tasks.md`, `task-templates.md`, `supporting-templates.md` and the scaffold files needed below. A global install is usable only when these files exist; its name or SKILL.md alone does not establish saved-task support. If complete, point instructions there and copy nothing. If incomplete, report the missing files and ask the owner to choose a complete project-local copy from the current release (recommended), use a complete workspace copy, or approve updating the global install. Do not select the incomplete install, silently update it, or claim setup is complete. When no usable global install exists, ask whether to copy `personal-memory` into the project's `.agents/skills/` or always open the project with their workspace. Recommend a self-contained copy of the entire personal-memory folder (including tasks.md, task-templates.md and supporting-templates.md) without `tests/` and `__pycache__`; explain workspace updates will not update it. Codex and Claude Code find it there. In Claude Cowork, an existing `personal-memory` skill loader works when this folder is attached, so save one only if none exists. Settle what the owner tracks with [tracking-model.md](tracking-model.md) before sorting; complete its proof only after approval in step 6.
3. **Set up memory if absent.** With the owner's OK, copy the six memory files from `<skills>/personal-memory/scaffold/` into `memory/`; the seventh file, `AGENTS-memory.md`, is an instructions snippet. Apply the approved tracking model: set `topics`, `client_folder`, `client_subjects` and `client_dirs` in `memory/schema.json`; do not carry client document defaults into a project-only layout. Create `memory/decisions/index.md` and `memory/workflows/index.md` with their parent folders by running `python3 <skills>/personal-memory/indexes.py`, or without Python write each by hand with its Decision Index or Workflow Index heading and no entries yet, using `memory/TEMPLATES.md` and personal-memory's manual checks when adding notes. Paste the snippet's sections below the comment into the folder's instructions file, creating `AGENTS.md` if absent and preserving existing content; replace `<skills>` with the chosen path. In git, add `memory/raw/` and `/.memory-recovery/` to `.gitignore`; ensure the recovery exclusion also exists when updating existing memory. Existing `memory/` otherwise skips this step. Release copies exclude recovery; upgrades leave old recovery intact and copy it separately only with owner approval. Before replacing existing hand-written notes, use personal-memory reference.md Recovery before editing, including verified file-tool copying without Python.
3a. **Set up saved tasks.** At approved memory setup or an explicitly approved tasks upgrade, read `<skills>/personal-memory/tasks.md`. If `tasks/index.md` is absent, follow tasks.md Start: use the Active index template, search existing task records and restore rows for active/waiting records; only a workspace with no unfinished records gets an empty index. Keep archived records out; no fictional tasks. If it exists, preserve its content and all task/archive/proposal records, never reset it. This also applies when existing memory skipped step 3. Keep personal-memory's chosen project/global location reachable from instructions; its installed task and supporting templates are the only format dependency, not external authoring skills or design docs. Add `/.task-recovery/` to Git ignores alongside memory recovery. Release copies exclude both recovery directories; upgrades retain existing recovery and copy it separately only with owner approval. Reads alone do not create an index. Without Python/Git use file tools and tasks.md's verification/stop rules.
3b. **Reconcile startup on an approved tasks upgrade.** Existing memory needs this step too. Before editing existing `memory/rules.md`, follow personal-memory reference.md "Recovery before editing"; preserve the instructions file's exact prior content too. Reconcile only the startup and Writing and saved tasks sections from `<skills>/personal-memory/scaffold/AGENTS-memory.md`, substituting the chosen skills path; retain unrelated owner instructions and honor the app's instruction-size limit. Add an optional `tasks/index.md` Always pointer and the saved-task bookkeeping row from `<skills>/personal-memory/scaffold/rules.md` if absent. Remove only the starter's `memory/preferences/writing.md`, `memory/preferences/diagrams.md` and `memory/preferences/document-scaffolding.md` pointers from Always rows, preserving every other owner pointer/row. Keep those existing files reachable on matching triggers: substantive drafting/editing; systems, flows or relationship explanations/planning; and creating/saving/organizing documents (including tasks), respectively. Add no preference pointer for a missing file. Retain any matching existing triggers instead of duplicating them. If customized instructions conflict with this approved change, ask rather than overwriting them. Verify the resulting rules and startup instructions, unchanged task/index/archive contents, and exact recoverable prior rules before reporting the upgrade complete; run the audit or disclose manual checks.
4. **Code or wiki source?** Read [code-repos.md](code-repos.md) before sorting; account for every reader of the old source before proposing removal.
5. **Sort the source.** Use [sorting.md](sorting.md) and destinations in [where-things-go.md](where-things-go.md). Sort small sources here. Above roughly 100 items or pages, available subagents may sort read-only batches with [subagent-brief.md](subagent-brief.md); spot-check their evidence and all input coverage. Without subagents, sort the same batches here.
6. **Show and wait.** Follow sorting.md's Presenting section: group kept items by destination, explain dropped items with counts and examples, and show backlog destinations. Ask once per group for this migration of old material; everyday capture in personal-memory needs no OK. Write no migrated content and delete nothing until the owner approves that group.
7. **Write approved notes.** Use `personal-memory`, `memory/README.md` and `memory/TEMPLATES.md`. Add one `memory/rules.md` row per kept note a task should load, glossary rows and index rows. With Python, run `python3 <skills>/personal-memory/indexes.py`, then `python3 <skills>/personal-memory/hubs.py`, then `python3 <skills>/personal-memory/gate.py --memory memory audit`; fix safe structural findings, but stop and report incomplete legacy procedures or other owner-repair-only findings instead of inventing dates or looping. Otherwise write indexes and hubs by hand and use personal-memory's manual checks.
8. **Retire only the approved local source.** Archive uncommitted content outside the folder, verify the archive, sort that content too and get approval under steps 5-6, then remove the approved source; follow code-repos.md for live references. An external source (another app or old workspace) stays untouched. Without a verified archive of content lacking committed history, leave the local source in place.
9. **Check and finish.** Run project tests if code changed. In git, stage only your own paths, run hooks (never `--no-verify`) and commit; push only if the project already pushes and the owner agrees. If git's configured hooks cannot run or fail for reasons outside this change, leave your paths staged, list them and tell the owner the commit is theirs to make rather than bypassing the hooks. Without git, finish with the file checks. Tell the owner what moved where, what stayed behind and why, and which checks were unavailable.
